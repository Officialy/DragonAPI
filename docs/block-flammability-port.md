# Block flammability catalogue — D23, Minecraft 26.3

## Source contract and repair

DragonAPI `de1bcf1f:Extras/BlockProperties.java` classifies planks, both log and leaf
families, wool, wooden slabs (including doubles), the four then-existing wooden stairs,
note blocks, jukeboxes, tall grass, dead bushes, TNT, bookshelves and vines as flammable.
The accepted port had commented out the common wood/leaves/wool/slab entries rather than
replacing the old metadata-based block identities. Finding 1.18 is confirmed for the
world-free catalogue. The world helper already consulted NeoForge's flammability hook,
so it was not universally broken for ordinary wood; however, it passed the block's dry
default state instead of the actual world state, defeating native waterlogging checks.

`BlockProperties.setFlammable()` remains a functional public initializer. It installs a
live state predicate over the native `FireBlock` burn-odds data plus
`#dragonapi:legacy_flammable`. It does not snapshot registry entries or tag contents.
The original `isFlammable(Block)` API delegates through the block's default state; a
new state overload retains actual waterlogging. The native table is the backing data
of NeoForge's default `getFlammability`, and is appropriate for this world-free catalogue.
Contextual block overrides require a world/position and belong in the world helper.

Native 26.3 fire data includes logs, stripped logs/wood, planks, leaves, slabs and stairs
of modern flammable species, including Poplar and bamboo, as well as all sixteen colours
of wool, wool stairs/slabs and carpet. Doubled wooden slabs remain flammable. Crimson and
warped wood retain native fireproof behavior. The two legacy catalogue entries absent
from native fire data—note block and jukebox—are generated by
`DragonAPIBlockTagsProvider` into `data/dragonapi/tags/block/legacy_flammable.json`.
Datapacks can add/remove these catalogue exceptions with standard tag semantics.
Waterlogged states remain excluded from this fallback even when their block is tagged.
The tag does not assign native fire-spread or burn odds.

`ReikaWorldHelper.flammable(BlockGetter, BlockPos)` now captures the actual state and
passes it to the contextual flammability hook and the catalogue fallback. Its original
air, chest and trapdoor exclusions are retained, as is the original UP face and numeric
flammability contract. A modded block's contextual positive result remains authoritative;
the world-free catalogue does not fabricate those results. ReactorCraft graphite is an
accepted example: its native override returns 70, while its world-free catalogue entry
has neither native vanilla fire odds nor a legacy tag entry.

## Accepted callers and validation boundary

The shared helper is used by DragonAPI `TemperatureEffect.IgnitionEffect`, RotaryCraft's
laser gun block-conversion path and ReactorCraft plasma's `onEnterBlock`. Native fixtures
exercise those actual entry points with common wood, wool, legacy note blocks and wet
slabs. The graphite fixture checks every registered reactor material: only graphite has
the contextual flammability override. There is no deletion or replacement of caller logic.

Three unit regressions cover original and modern common wood, every wool colour/shape,
all wooden slab types, repeated policy initialization and dry/wet states. Five new
DragonAPI native tests cover the complete registered catalogue against live native/tag
data, generated legacy exceptions, fireproof Nether wood, actual world states and
original chest/trapdoor exclusions, tag additions/removals/restoration, temperature
ignition and the public laser beam entry point. Two ReactorCraft native tests cover
graphite and actual plasma entry behavior.

The tag-rebinding fixture invokes the native `prepareTagReload(...).apply()` path
synchronously and restores every original binding in `finally`. This validates live
membership after reload application; it does not claim to exercise a full resource-pack
discovery/JSON loading cycle. The datagen run separately validates the generated JSON.
Client render/input and remote-client acceptance are outside this change.

Validation results are recorded in `PORT-AUDIT-REVIEW.md` and the project backlog.
